# Wazuh demo wiring

This folder contains the Windows Agent configuration example and a sample Wazuh rule file for the canonical IDS events emitted by `live_traffic_simulator.py`.

The pipeline is replay-based streaming detection, not live packet capture.

Windows host:

Hybrid IDS -> logs/live_security_events.jsonl -> Wazuh Agent -> 127.0.0.1:1514 -> VirtualBox NAT -> 10.0.2.15:1514 -> Ubuntu Wazuh Manager

For a confirmed smoke test, you can point the agent at `logs/smoke_live_security_events.jsonl` instead of the default live replay file.

Enrollment path:

Windows Agent -> 127.0.0.1:1515 -> VirtualBox NAT -> 10.0.2.15:1515 -> Wazuh authd

## Agent side

Configure the Windows agent to monitor only the JSONL output generated by the simulator. Replace `REPLACE_WITH_YOUR_REPO_PATH` with the actual absolute path to your repository root on Windows.

Example `ossec.conf` snippet:

```xml
<client>
  <server>
    <address>127.0.0.1</address>
    <port>1514</port>
    <protocol>tcp</protocol>
  </server>
</client>

<localfile>
  <location>REPLACE_WITH_YOUR_REPO_PATH\logs\smoke_live_security_events.jsonl</location>
  <log_format>json</log_format>
</localfile>
```

If you want the agent to follow the normal replay pipeline instead, change the path above to `REPLACE_WITH_YOUR_REPO_PATH\logs\live_security_events.jsonl`.

For a clean Discover view that shows only the hybrid IDS alerts, remove or comment out any other `<localfile>` entries in the Windows agent config, especially Windows EventChannel sources. The demo should ship exactly one monitored source: the JSONL file above.

For enrollment, use manager address `127.0.0.1` and port `1515`. Keep the protocol on TCP for the event channel.

If you prefer to keep a copy alongside the repo, see `windows-ossec.conf.example`.

## Ubuntu manager side

Copy `hybrid_ids_rules.xml` to the manager rules directory, validate the XML/rules,
then restart the manager:

Recommended path on Ubuntu:

```bash
sudo cp hybrid_ids_rules.xml /var/ossec/etc/rules/
sudo chown wazuh:wazuh /var/ossec/etc/rules/hybrid_ids_rules.xml
sudo /var/ossec/bin/wazuh-logtest
sudo systemctl restart wazuh-manager
```

Paste one complete JSON line from `logs/smoke_live_security_events.jsonl` into
`wazuh-logtest`. The JSON decoder is built in; do not install the legacy syslog
decoder for the JSONL agent path. Confirm that `100100` and, where applicable,
`100101` or `100102` fire.

Check manager health and rule loading:

```bash
sudo systemctl is-active wazuh-manager
sudo tail -f /var/ossec/logs/alerts/alerts.json
sudo grep -i hybrid_ids /var/ossec/logs/ossec.log
```

For the Windows agent path, the manager must be reachable on TCP `1514` and the
agent enrollment service on TCP `1515`. If the IDS runs on Ubuntu instead, replace
the Windows `<localfile>` with:

```xml
<localfile>
  <location>/opt/hybrid-ids/logs/live_security_events.jsonl</location>
  <log_format>json</log_format>
</localfile>
```

Do not enable destructive active response initially. First validate alert rates for
at least one capture window. After approval, bind an active response only to a
high-confidence custom rule and require a human approval service or allowlist for
production networks.

If `wazuh-logtest` shows only a default rule such as `86600 Suricata messages`, the custom rule file is not yet loaded in the manager or the manager has not been restarted.

The sample rule IDs stay inside the custom range recommended for local rules.

## Verification checklist

Windows:

```powershell
Test-NetConnection 127.0.0.1 -Port 1514
Test-NetConnection 127.0.0.1 -Port 1515
```

Both should return `TcpTestSucceeded : True`.

Restart the agent service:

```powershell
Restart-Service -Name wazuh
Get-Service wazuh
```

Ubuntu:

```bash
sudo /var/ossec/bin/agent_control -l
sudo /var/ossec/bin/wazuh-logtest
```

Use `wazuh-logtest` by pasting one JSON line from `logs/smoke_live_security_events.jsonl` and confirm a custom rule fires. The event should look like the canonical JSON emitted by the replay simulator and include fields such as `event_type`, `detection.prediction`, `risk.severity`, `mitre.technique`, and `threat_intelligence.reputation`.
P1 events additionally contain `risk.priority: P1` and
`workflow.status: PENDING_REVIEW`; these are queued for analyst approval and do
not trigger blocking by themselves.

After reviewing an event, record the decision locally:

```bash
python scripts/review_alert.py alert.json reviewed-alert.json \
  --decision approve --reviewer analyst-1 --action COLLECT_EVIDENCE
```

Use `BLOCK_SOURCE` or `ISOLATE_HOST` only as a reviewed request. The workflow
records `executed: false`; it does not perform a network change.

To focus Discover on the IDS output during the presentation, use a query like `rule.groups:hybrid_ids` or `location:\"C:\\Users\\heerm\\projects\\Hybrid-Threat-detection-ids\\logs\\smoke_live_security_events.jsonl\"`.
